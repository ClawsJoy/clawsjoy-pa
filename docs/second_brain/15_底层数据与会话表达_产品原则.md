# 产品原则：底层数据机关 ＋ GPT 式表达层

> 2026-10-30 · 产品原则 ｜ 好的 PA 不是“操作台”，而是“会沟通的私人助手”

## 一、一句话

**底层善于处理本地数据、上下文、归档、摘要、采集；前台像 GPT 一样善于沟通和可视化。**

## 二、两层分工

### 底层：数据与上下文机关

负责：

- 本地数据接入：笔记、文件、语音、录屏、浏览器、台账；
- 归档：原件、附件、版本、去重、保留策略；
- 索引：全文、向量、时间线、项目/人物/主题；
- 上下文：会话历史、摘要、任务状态、画像、偏好；
- 采集：自动/手动收集，来源与权限可追；
- 证据：出处、页码、时间码、文件路径；
- 权限：读/写/外发/凭据分层。

底层要求：

- 确定性、可审计、可重建；
- 不编数据；
- 空就是空，缺就是缺；
- 数据属于用户，可导出、可清空。

### 前台：沟通与可视化

负责：

- 自然对话，像 GPT 一样接话、追问、解释；
- 流式输出，不让用户干等；
- 富卡片：笔记、视频、任务、来源、图表；
- 渐进披露：先结论，再细节；
- “为什么这么答”可展开证据；
- 错误说人话，不甩内部诊断。

前台要求：

- 不冒充事实；
- 不把内部脚手架当答案；
- 不在默认界面堆诊断信息；
- 不让用户感觉在操作一台机器。

## 三、关键边界

| 事项 | 归底层 | 归前台 |
|---|---|---|
| 事实/数字/出处 | 是 | 不能编 |
| 语气/接话/追问 | 否 | 是 |
| 能力清单 | 是（事实卡） | 是（自然表达） |
| 会话摘要 | 是 | 是（展示） |
| 模型选择 | 是（路由/权限） | 是（状态可见） |
| 错误原因 | 是（机器字段） | 是（人话解释） |
| 权限审批 | 是 | 是（解释清楚） |

## 四、PA 现状

### 已经较强的底层

- 第二大脑 Markdown + 索引；
- 本地文件/语音/录屏/浏览器采集；
- 事件、会话、台账、回执；
- 本地 qwen + Ollama；
- 来源与证据链。

### 明显偏弱的前台

- 自述/能力问答被前端规则拦截，不调模型；
- /v9/pa/ask 是检索面，不负责自然对话；
- 对话整段返回，不是流式；
- 缺 key 时直接报错，不回退本地；
- 默认界面容易露出判据/面册/工程字段；
- 画像为空被说成“后端未应答”。

## 五、下一阶段优先级

1. **事实/表达分离**：事实卡只作模型上下文，模型自然说；
2. **本地默认生成**：qwen 优先，云端可选；缺 key 回退本地；
3. **流式会话**：首 token 要快，正文逐字出；
4. **上下文机关**：会话摘要、画像、归档、时间线；
5. **GPT 式前台**：聊天为主，卡片为辅，证据可展开；
6. **错误与人话**：诊断进详情，不占主屏。

## 六、反模式

- 把内部判据、面册、源码片段直接甩给用户；
- 用固定口径回答所有“你是谁/能做什么”；
- 把检索拒答当成聊天；
- 让用户等几十秒才看到整段；
- 缺 key 就失败，而不是回退本地；
- 让聊天界面承担数据管理职责。

## 七、验收

- 用户感觉在和一个助手说话，不是查系统；
- 答案有出处，但不把出处堆满屏；
- 本地数据越用越懂用户；
- 模型不可用时，产品仍然可用、说实话；
- 关掉模型，数据与归档仍然成立。
