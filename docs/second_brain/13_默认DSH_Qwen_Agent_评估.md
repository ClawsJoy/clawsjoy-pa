# 默认内置 DSH + Qwen Agent？评估与建议

> 2026-10-30 · 产品评估 ｜ 是否给 PA 默认内置一个 DSH + qwen 通用执行 Agent

## 一、结论

**可以做，但建议做成 PA 下属的“第一方通用执行 Agent 配置”，不做成 PA 内部隐藏的第二套系统。**

- 默认**可见**：用户能看到它在跑、用什么模型、拿哪些权限；
- 默认**可关**：一键停用；
- 默认**读写分级**：读可自动，写/删/发/支付必须审批；
- 默认**本地 qwen**，云端 API 仅显式选配；
- 不把 DSH 全量 UI/市场默认塞进 PA。

## 二、为什么值得做

1. PA 不是空壳：新用户首启就能办事，而不是只有聊天和检索；
2. 复用本地 qwen，不重复装模型；
3. DSH 的工程/工具能力可以补 PA 的执行面；
4. 符合 PA 定位：**PA 编排上层 agent**，DSH 只是其中一个被管理的 agent；
5. 用户可以先体验，再决定是否接更多 agent。

## 三、风险

| 风险 | 说明 | 对策 |
|---|---|---|
| 两套系统 | PA 与 DSH 各一套会话/权限/更新 | 只把 DSH 当执行引擎，不暴露第二套主界面 |
| 安全 | Agent 可读文件/跑命令 | 工作区沙箱 + 写操作审批 + 默认只读 |
| 体积 | Node 运行时/插件包 | 可选安装或按需下载，不默认全量 |
| 资源 | qwen 7B + agent 并发 | 并发上限 + 队列 + 可关 |
| 版本耦合 | DSH API 变化 | 固定版本；兼容矩阵；失败回退 PA 原生 |
| 用户困惑 | “PA 和 DSH 谁在说话” | 统一显示“执行席位：DSH·qwen”，不另开人格 |
| 数据边界 | Agent 接触第二大脑 | 明确授权范围；默认只读工作区 |

## 四、建议形态

~~~text
PA（主脑 · 编排 · 信任根）
  └─ 执行席位：通用 Agent
       引擎：DSH
       模型：local:ollama / qwen2.5:7b
       权限：workspace 只读（默认）
             写入/命令/网络 ⇒ 逐次审批
       可关：设置 → 能力 → 通用执行 Agent
~~~

### 不推荐

- 把 DSH 作为 PA 的隐藏后端；
- 默认给 shell/文件写权限；
- 默认启用 DSH 插件市场；
- 默认让 DSH 接管 PA 的会话/记忆。

## 五、默认策略

| 项 | 默认 |
|---|---|
| 启用 | 首启向导询问，默认建议开启 |
| 模型 | 本地 qwen |
| 读取工作区 | 允许 |
| 写入/删除 | 需审批 |
| 执行命令 | 需审批 |
| 网络 | 默认关闭，按任务开 |
| 云端 API | 关闭，用户选配 |
| DSH 插件市场 | 不默认开 |
| 可停用 | 是 |

## 六、MVP

1. PA 增加“执行席位：通用 Agent”卡片；
2. 固定 DSH 版本 + qwen 本地模型；
3. 工作区只读 + 写操作审批；
4. 任务卡显示“PA 分派 → 通用 Agent”；
5. 失败回退 PA 原生能力；
6. 设置里可关、可换模型、可改权限。

## 七、分阶段

- **P0**：PA 原生能力 + 本地 qwen 聊天（已有基础）；
- **P1**：DSH 通用 Agent 适配器（只读 + 审批）；
- **P2**：多 Agent 席位、插件/技能分配；
- **P3**：市场与 DSH 兼容层。

## 八、判断标准

上线前必须能回答：

- 用户是否知道当前是谁在回答？
- 用户是否知道 Agent 拿了哪些权限？
- 写操作是否逐次可见、可拒？
- 关掉 Agent 后 PA 是否仍可用？
- DSH 升级坏了，是否自动回退 PA 原生？

答不上来，就不该默认开启。
