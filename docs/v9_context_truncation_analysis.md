# V9 上下文截断策略分析报告

> 目的：为 system 消息瘦身与工具调用结果保留做准备。
> 分析对象：`agent_gateway_enhanced.py`（V9 网关）、`core/lib/sandbox_tools.py`（项目树生成）。
> 日期：2026-07

## 1. `_hard_truncate_messages` 当前截断逻辑

**位置**：`agent_gateway_enhanced.py`（约 L7250 附近，400KB 硬上限兜底路径调用）。

**逻辑要点**：

| 项 | 现状 |
| --- | --- |
| 触发条件 | 总上下文超硬上限（约 400KB）时调用 |
| 截断对象 | 仅 `role == "system"` 且内容长度 > `_sys_limit` 的消息 |
| `_sys_limit` 实际值 | **8000 字符**（代码实测） |
| 截断方式 | 保留 `content[:300]`（头部）+ 截断标记 + `content[-1500:]`（尾部），中段整体丢弃 |
| 非 system 消息 | **不截断**，user/assistant/tool 原样保留 |

**⚠️ 发现的不一致**：函数 docstring 注释仍写"丢弃 2000 字符以上的 system"，代码实际用 8000 —— 注释与实现脱节，需修正注释或统一常量。

**核心矛盾**：兜底截断只对 system 消息生效，而上下文膨胀的主因往往是超大 tool 调用结果（read_file 大 JSON、query_index 长结果）—— 这两类消息被原样保留，瘦身没有打在最痛处。

## 2. system 消息内容构成与占比

主 chat 生成路径（约 L7025-7050）中，system 消息由 4 层拼接：

| 层 | 内容 | 估算字符数 | 估算 tokens | 备注 |
| --- | --- | --- | --- | --- |
| ① base prompt | 岗位能力 + 工具声明 + 收尾 SOP + 元认知规则 + 拆解反馈闭环 | ~3500-4500 | ~1200-1500 | 静态模板，最稳但最长 |
| ② 精准投喂 | SAG 注入 + 过滤网权重 Top10 + 系统假设 + 计划讨论 | ~2500-4000 | ~800-1300 | 受 `max_sys_chars=8000` 约束 |
| ③ 项目树 | `_project_tree`（>50 文件 → 摘要模式） | ~1500-2500 | ~500-800 | 文件多时摘要化 |
| ④ 路径+配额 | 路径前缀 + 读取配额提示 | ~200 | ~60 | 最短 |

**约束**：`_inject_sys_content(sys_msgs, max_sys_chars=8000, ...)` —— 精准投喂段总长被压在 8000 字符（≈2500 tokens）内。

**结论**：base prompt（①）是最大固定开销；项目树（③）在单仓库超 50 文件时已走摘要模式，优化空间有限；**可压缩空间集中在 ①（冗余段落）与 ②（低价值注入）**。

## 3. 截断后 tail:2 保留的是什么

**逻辑**（400KB 兜底路径）：
```python
tail = [m for m in messages[-3:] if m["role"] != "system" and m not in learning_msgs[-5:]]
```
从最近 3 条消息中过滤掉 system 和 learning 消息，保留结果通常为 2 条（tail:2）。

**结论**：tail:2 保留的是**最近轮次的 assistant 回复或 tool 调用结果**，具体取决于最近会话形态：

- 若最后一条是 assistant 文字回复 → 保留的是文字回复 + 更早一条
- 若最后一条是 tool 调用（如 read_file 返回大 JSON）→ 保留的是 **tool 结果**，可能把更早的 assistant 总结挤掉

**风险点**：当前 tail 选择不区分消息类型，tool 结果（长、低信息密度）可能挤占 assistant 文字回复（短、高信息密度）的保留位。瘦身时建议对 tool 结果做摘要保留而非整体保留。

---

## 4. 优化建议（为瘦身与 tool 结果保留做准备）

1. **修正 `_sys_limit` 注释**：docstring 的 2000 → 8000，或提取为命名常量 `SYS_TRIM_LIMIT`。
2. **system 消息内分层裁剪**：超限时按优先级裁剪——先裁 base prompt 尾部的元认知/拆解闭环冗余段，再裁 SAG 注入低价值段，最后才动项目树。
3. **tool 结果摘要保留**：对超大 tool 结果执行 `content[:2000] + "...截断标记..." + content[-500:]`，而非整条保留/丢弃，保住关键头尾（如 read_file 的路径与行号）。
4. **tail:2 类型感知**：若最近一条是 tool 结果，向前回溯到最近一条 assistant 文字回复，保证高密度信息留在上下文。
5. **项目树动态降级**：上下文紧张时从"摘要模式"再降级为仅顶层目录列表（省 ~1000 字符）。
6. **注入预算透明化**：在 system 消息末尾追加各段字符数统计，便于运行时观测占比（为瘦身效果验证提供数据）。
